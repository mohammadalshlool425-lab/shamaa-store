# البنية والقرارات التقنية · Architecture

## 1. اختيار المرحلة الأولى

**تطبيق واحد معياري**: FastAPI + REST API + واجهة JavaScript محلية + SQLite على قرص دائم بخادم واحد. هذا يقلل تكلفة البداية والتبعيات والخدمات المدفوعة، دون تقديمه كبنية توسع أفقي جاهزة.

```text
المتصفح / PWA
  │ HTTPS، نطاق واحد، Cookie + CSRF، JSON
  ▼
وكيل TLS موثوق في الإنتاج
  ▼
FastAPI
  ├─ accounts / catalog / seller / orders / admin
  ├─ commerce + authorization + audit
  ├─ SQLite (WAL افتراضيًا): معاملات ومخزون وطلبات وصندوق إرسال
  └─ وسائط خاصة مطبّعة على قرص دائم
       │
       ├─ mail-worker → SMTP/TLS بعد إعداد المشغّل
       └─ backup job → archive AES-GCM → نسخة خارجية يجهزها المشغّل
```

- Node خاص بأدوات التطوير/المتصفح، لا runtime ولا build مطلوبين لخدمة الواجهة.
- الخطوط والأيقونات والصور التوضيحية محلية؛ لا CDN أو متعقب تحليلات أو اتصال AI خارجي.
- `server/application.py` مصنع بلا تهيئة قاعدة عند استيراده؛ الاختبارات تمرر إعدادات معزولة. `server/main.py` فقط ينشئ تطبيق التشغيل.
- `server/wsgi.py` يغلّف نفس مصنع FastAPI اختياريًا بـa2wsgi للمعاينة HTTP/WSGI؛ لا يستورد التطبيق أو يهيّئ قاعدة بمجرد استيراد الوحدة. `SHAMAA_SQLITE_JOURNAL_MODE=DELETE` خيار مقيد لهذه المعاينة، وليس ترقية توسع أو ضمانًا لصلاحية أي نظام ملفات. WebSockets وASGI lifespan hooks ليست ضمن هذا المسار.
- روابط البريد الجديدة تستخدم `#token=` بدل query، ويحتفظ المتصفح بالرمز في الذاكرة حتى POST، مع إزالة الرمز من شريط العنوان؛ الروابط القديمة تبقى متوافقة.
- `main.py` و`app.py` يشيران إلى التطبيق نفسه؛ لا منصتان مختلفتان ولا نسخة Streamlit موازية.

## 2. نموذج البيانات

| الكيان | الضمان الأساسي |
|---|---|
| users | بريد فريد، أدوار buyer/seller/admin، حالة وتأكيد بريد، سر MFA مشفّر للمشرف |
| sessions / auth_tokens | تجزئة الرموز الأصلية؛ صلاحية زمنية وإبطال؛ رمز بريد أحادي الاستخدام |
| stores | مالك وحيد، متجر واحد للمالك، slug فريد، مراجعة وشحن مستقل |
| categories | تسلسل أم/فرع، نسبة اختيارية؛ المعدلات لا تظهر في الكتالوج العام |
| products / media | SKU فريد داخل المتجر، نسخة تفاؤلية، مخزون غير سالب، ملكية الصورة |
| carts | سلة دائمة لكل مستخدم، منتج/كمية فريدان |
| orders | الطلب الأب، بيانات التسليم، المجموع الأصلي، مفتاح تكرار فريد داخل حساب المشتري |
| seller_orders / order_items | شحنة لكل متجر، أسماء وأسعار وكميات ونسب عمولة وقت الطلب |
| order_events / inventory_movements | سجل غير قابل للتعديل أو الحذف عبر triggers |
| ledger | قيد COD مستحق مرة واحدة عند التسليم؛ ليس حسابًا مصرفيًا أو دفترًا محاسبيًا عامًا |
| audit_log | سجل إلحاق فقط للقرارات الإدارية/الأمنية |
| mail_outbox / notifications | إشعار داخل الحساب ورسالة طابور مرتبطة بمعاملة الأعمال |
| settings | العمولة العامة ونصا العنوان؛ لا أسرار مزوّدين في هذه البيانات |

المخطط `PRAGMA user_version=1`. لا ترحيل تلقائي من قاعدة المشروع القديم. إن كانت القاعدة أحدث من التطبيق، يُرفض تخفيض المخطط. إضافة مرحلة جديدة تستلزم ترحيلًا مرقّمًا واختبار ترقية/استعادة، لا تعديل جداول إنتاج يدويًا.

## 3. المال والعمولات

**1000 فلس = 1 JOD**. جميع حقول المال أعداد صحيحة؛ تحويل إدخال الواجهة العشري يتم بتقسيم نصي، لا بضرب float.

- `commission_bps`: أساس من 10000؛ `500` = 5%، `0` نسبة صريحة وليست «فارغ».
- الأولوية: تخصيص المتجر ← الفئة المباشرة ← الفئة الأم الواحدة ← العام.
- هيكل التصنيفات الحالي مستويان؛ الوراثة لا تصعد سلسلة غير محدودة من الأجداد.
- الافتراضي 500 bps؛ الحد المسموح للإعداد 5000 bps، وليس وعدًا بأن 50% مناسب تجاريًا.
- الحساب لكل سطر، على `سعر البيع × الكمية` دون الشحن:

  ```text
  commission_fils = (line_total_fils × bps + 5000) // 10000
  seller_order.net_fils = subtotal_fils + shipping_fils - commission_fils
  ```

- هذا تقريب نصف إلى أعلى للفلس؛ تجميع العمولات يكون بعد تقريب كل سطر.
- سعر المقارنة ليس خصمًا إضافيًا؛ سعر البيع هو المبلغ المدفوع. لا كوبونات/ضرائب محسوبة/رصيد نقاط حاليًا.
- COD: البائع/السائق يستلم النقد خارج المنصة. `net_fils` قيمة محسوبة **وليست رصيد سحب**. `cod_commission_due` دين مستحق عند التسليم وليس إثبات تحصيل. تسوية هذا الدين تحتاج إجراءات تجارية/قانونية؛ لا زر تحصيل مزيف أو تحويل بنكي.
- تغيير المعدلات لا يعيد كتابة نسب أو أسعار الطلبات السابقة.

## 4. سلامة الطلب والمخزون

1. الواجهة تطلب عرض سلة محسوبًا من الخادم ومجمّعًا حسب المتجر.
2. ترسل بيانات التسليم و`expected_total_fils` و`quote_hash` ومفتاح `Idempotency-Key` عشوائيًا. لا ترسل أسعارًا معتمدة من العميل أو نسبة يختارها المشتري.
3. `BEGIN IMMEDIATE` يسلسل كتابة SQLite. داخل **المعاملة نفسها**: يُفحص التكرار، وحالة المنتجات/أصحاب المتاجر والمخزون والعرض، وتُنشأ الشحنات والسطور، ويُخصم المخزون وتُكتب الأحداث والإشعارات وتُفرغ السلة.
4. الخصم شرطه `stock >= quantity`؛ أي فشل يُرجع المعاملة كلها. ليس هناك بيع جزئي غير مقصود من طلب متعدد المتاجر.
5. نفس المفتاح ونفس الطلب يرجعان الطلب السابق؛ استعماله لبيانات مختلفة يرجع `409`. التفرد مقيد بالمشتري، فلا يكشف مفاتيح حساب آخر.
6. عند ضياع استجابة الشبكة، `GET /api/order-attempts/{key}` يعيد طلب **الحساب الحالي فقط**؛ لا يُنشأ مفتاح جديد لمجرد أن المستخدم لم ير رسالة النجاح.
7. السلة لا تحجز المخزون. تغير السعر/الشحن/المنتج/التوفر قد يستلزم عرضًا جديدًا قبل الشراء.
8. الإلغاء المسموح يعيد المخزون مرة واحدة ويسجل حركة، ولا يعيد كتابة المجموع الأصلي. `live_total_fils` يحسب الشحنات غير الملغاة.

الحالات:

```text
new → confirmed → preparing → shipped → delivered
  └───────┴───────────┘ → cancelled (حسب الدور)
```

المشتري يلغي new/confirmed فقط. البائع/المشرف يمكنهما إلغاء قبل الشحن وفق انتقالات الخادم. لا رجوع من delivered ولا إرجاع/استرداد بعد الشحن في هذه المرحلة. `expected_status` ونسخة المنتج يمنعان الكتابة فوق تعديل متزامن قديم. التسليم ينشئ قيد العمولة الفريد ولا يثبت قبض النقد.

## 5. حدود الصلاحيات

| العملية | زائر | مشتري | بائع | مشرف + MFA |
|---|---|---|---|---|
| كتالوج ومتاجر منشورة | نعم | نعم | نعم | نعم |
| سلة/طلب شخصي | سلة أجهزة فقط | حسابه، والتأكيد للطلب | حسابه، لا يشتري منتجه | حسابه فقط عبر مسارات المشتري |
| إنشاء متجر | لا | بعد تأكيد البريد | متجره فقط | لا ترقية أدوار عامة من الواجهة |
| منتج/صورة/مخزون | لا | لا | متجره وصوره فقط | مراجعة ونشر، لا انتحال ملكية البائع |
| شحنات البائع | لا | لا | شحناته فقط وبيانات التسليم اللازمة | جميعها |
| إعداد نسبة/واجهة | لا | لا | لا | كلمة مرور + TOTP حديث خلال 10 دقائق |
| users/audit/ledger | لا | لا | لا | نعم |

كل هذه الحواجز على الخادم، وليست إخفاء تبويب. المشرف يُنشأ من CLI خاص، ولا يوجد حساب أو كلمة مرور عامة. إنشاء المشرف إجراء bootstrap موثوق لمشغّل الخادم، لا ادعاء تحقق خارجي من هوية صاحبه. أدوار موظفي المحاسبة والدعم والتسويق بالعمولة وصلاحيات الأعمال المتعددة ليست مفعّلة بعد.

## 6. البريد والوسائط وPWA

- صندوق الإرسال ضمن نفس المعاملة. عامل مستقل يدعم مهلة حجز وإعادة محاولة حتى 5 مرات مع تأخير، ورسالة Message-ID ثابتة. SMTP توصيل at-least-once؛ قد تتكرر رسالة بعد عطل في لحظة الإرسال، ولا نعد بتوصيل exactly-once أو نجاح الوصول إلى Inbox.
- ملفات `.eml` تطوير خاصة لا تعني إرسالًا حقيقيًا. رابط التأكيد لا يُستهلك بمجرد فتح GET؛ يلزم POST، حتى لا يستهلكه ماسح الروابط في البريد.
- JPEG/PNG/WebP فقط؛ فك وترميز فعلي وإزالة metadata، حد 5MiB و16Mpx، نسختان WebP 480/960. الصورة غير المنشورة متاحة لمالكها/المشرف فقط؛ لا تتاح مجلدات data عبر static.
- العامل الخدمي يحتفظ بالقشرة والموارد المحلية والكتالوج العام فقط، بحد 40 طلب كتالوج. لا يخزن `/api/auth` أو سلة/طلبات/إدارة أو `/media`، ولا يصف عمليات كتابة لإرسالها لاحقًا.
- HTML الصفحات الخاصة وواجهات البيانات الخاصة `no-store`. البيانات العامة المحملة سابقًا قد تكون قديمة دون اتصال؛ لا تثبيت لسعر أو توفر قبل التحقق عبر الشبكة.
- الروابط ووسوم عنوان/وصف أساسية وrobots/sitemap موجودة؛ لا JSON-LD لتقييمات غير موجودة، ولا وعد بأرشفة SPA أو ترتيب محركات البحث. SEO متقدم وتصوير الخادم الكامل لاحقًا.

## 7. طريق التوسع، بلا وعود زائفة

1. قياس الحمل الفعلي وحجم الوسائط ومعدل lock/5xx أولًا؛ لا أرقام تحمل مُدعاة بلا قياس.
2. قبل أكثر من مضيف: نقل SQLite إلى PostgreSQL مع ترحيلات، قفل صفوف/عمليات شرطية، واختبارات تنافس/تكرار جديدة. تغيير `SHAMAA_DB` إلى URL لا ينفذ ذلك.
3. تخزين كائنات خاص ونسخ خارجية، وطوابير عمل ومراقبة، بعد مقارنة الأسعار وحدود الاستخدام والتصدير وشروط التجارة.
4. دفع/شحن عبر adapters وwebhooks موقعة ومفاتيح خادم وخطة مصالحات؛ لا مجرد استبدال ثلاثة URLs.
5. Android يمكنه استهلاك API بعد إصدار API موثق وضبط المصادقة ودورة تحديث وإتاحة؛ **لا يوجد APK أو تطبيق Android الآن**.
6. AI لاحق، تعطيله هو الوضع الحالي؛ مزود قابل للتبديل، لا بيانات شخصية أو أسرار في المتصفح، ولا قرار مالي/احتيال نهائي من AI.
