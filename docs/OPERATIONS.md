# دليل التشغيل والنشر والنسخ والاستعادة

**هذا دليل وقوالب تحتاج إعدادًا، وليس تقرير نشر منفذ.** البيئة الحالية معاينة تطوير على منفذ 8000. لا خدمة SMTP خارجية أو مهام إنتاج/نسخ خارجية أو DNS/HTTPS أُنشئت نيابة عن المالك.

للمعاينة المجانية محدودة الحصة فقط يوجد [دليل PythonAnywhere/WSGI](DEPLOY_FREE_PYTHONANYWHERE.md). لا تنطبق عليه أوامر systemd أو افتراض وجود cron/عامل دائم أو قبول تشغيل إنتاج، ولم ينفذ إعداد حساب خارجي بعد.

## 1. متطلبات نشر المرحلة الأولى

- Linux محدث، Python 3.11 بأحدث تحديث أمني متاح، مستخدم خدمة غير root، وقرص دائم محلي.
- مضيف واحد/instance واحد/worker واحد كبداية. لا تشغيل SQLite على NFS/قرص مؤقت أو داخل عدة replicas.
- حساب مشغّل موثوق وMFA وصلاحيات ضيقة؛ الشفرة وvenv للقراءة فقط لمستخدم الخدمة، والبيانات خارج مجلد إصدار الشفرة.
- DNS ونطاق عام ووكيل TLS موثوق وشهادة وتجديد، وجدار ناري لا يعرض منفذ التطبيق 8000 للإنترنت. القالب يربط 0.0.0.0 لدعم المعاينة، ولا يعني السماح للعموم بتجاوز الوكيل.
- SMTP صالح للتجارة والنطاق، ونسخ خارجية، ومراقبة وفشل/تنبيهات، ومراجعة [الأمان والقانون](SECURITY_PRIVACY.md) و[التكلفة](COSTS.md).

هيكل مقترح، لا مجلدات أُنشئت على خادم خارجي بالفعل:

```text
/opt/shamaa/releases/<release>/   شفرة + .venv لإصدار محدد
/opt/shamaa/current              رابط الإصدار الجاري
/var/lib/shamaa/                 قاعدة وmedia، خاص بمستخدم shamaa
/var/backups/shamaa/             أرشيفات مشفرة محلية، خارج شجرة الويب
/etc/shamaa/production.env       إعدادات خاصة، مملوكة للمشغّل وبصلاحيات مقيدة
/etc/shamaa/backup.env           مفتاح نسخ منفصل يُحقن في مهمة النسخ فقط
```

النموذج لا ينفذ Docker أو استضافة serverless أو PostgreSQL تلقائيًا. مستخدم systemd المقترح `shamaa` يجب إنشاؤه وتملك مجلد البيانات/النسخ له قبل تفعيل الوحدات.

## 2. إعدادات الإنتاج

انسخ مفاتيح `.env.example` إلى ملف خاص للمضيف، **لا إلى Git أو static**، وعيّن:

| المتغير | المطلوب |
|---|---|
| SHAMAA_ENV | production |
| SHAMAA_DB | مسار مطلق مثل /var/lib/shamaa/marketplace.sqlite3 |
| SHAMAA_DATA_DIR | /var/lib/shamaa، لا جذر الملفات أو المشروع |
| SHAMAA_PUBLIC_URL | عنوان HTTPS العام الحقيقي، بلا مسار إضافي أو query، مثل https://your-domain |
| SHAMAA_ALLOWED_HOSTS | أسماء مضيف محددة تضم نطاقك، بلا * ولا localhost للإنتاج |
| SHAMAA_DEMO_DATA | 0؛ ابدأ بقاعدة نظيفة لم تُستخدم في التطوير |
| SHAMAA_EMAIL_MODE | smtp |
| SHAMAA_SMTP_HOST / PORT | من مزودك؛ 587 مع STARTTLS أو 465 مع TLS مباشر |
| SHAMAA_SMTP_USER / PASSWORD | إن تطلبهما المزود؛ من خزنة خاصة، لا في أوامر أو محادثة |
| SHAMAA_MAIL_FROM | عنوان نطاق وافق عليه مزود SMTP، لا noreply@example.com |
| SHAMAA_ENCRYPTION_KEY | مفتاح مستقل محفوظ في خزنة مع نسخة استعادة |

أنشئ مفتاح التطبيق محليًا في طرفية خاصة باستخدام `python -m server.cli generate-key` وانقله بطريقة آمنة إلى خزنة/ملف البيئة. **لا ترسل ناتجه في الدعم**. أنشئ مفتاحًا ثانيًا مختلفًا للنسخ واحفظه في `/etc/shamaa/backup.env` باسم `SHAMAA_BACKUP_KEY`، مع نسخة استعادة مستقلة خارج المضيف. ملف بيئة خدمة الويب لا يحتاج مفتاح النسخ.

الخادم يرفض إنتاجًا مع demo أو بريد file أو غياب مفتاح/SMTP أو HTTP/localhost أو wildcard hosts أو قاعدة تحتوي متاجر توضيحية/طلبات تطوير موسومة. هذا حاجز أخطاء شائع، **ولا يثبت** صلاحية النطاق أو DNS أو ملكية البريد أو جودة SMTP أو قانونية النشاط.

لا تبدل قاعدة تطوير إلى إنتاج لمجرد إزالة العلم؛ تمييز الطلبات التجريبية لا ينظف الحسابات/الصور التجريبية الأخرى. لا ترحيل من قاعدة المشروع القديم؛ خطط لترحيل البيانات منفصلًا بعد نسخة واختبارات.

## 3. تثبيت إصدار واختباره قبل التبديل

في مجلد الإصدار، على Linux/Python 3.11:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install --require-hashes -r requirements.lock
.venv/bin/python -m pip check
```

اختبر الإصدار على staging بقاعدة ومفاتيح منفصلة وبريد sandbox يخص الفريق فقط. لا تجعل staging يرسل للعملاء، ولا تنسخ بيانات شخصية إليه إلا وفق إجراء مشروع ومصغّر. يفضل وضع development على staging حتى لا يُفهرس؛ تغيير production.env لا يضيف إعدادات staging تلقائيًا.

شغّل الاختبارات المعزولة حسب README. تحقق يدويًا من إنشاء مدير/MFA، وتأكيد بريد فعلي باللغتين، ومتجر ومنتج وطلبين متزامنين محدودين، وحالة إعادة الطلب، ومن عدم تسرب بيانات في headers/logs.

في الإنتاج لأول مرة، مع متغيرات البيئة الخاصة محملة **بآلية المشغّل الموثوقة**:

```bash
.venv/bin/python -m server.cli init
.venv/bin/python -m server.cli create-admin
```

هذه أوامر محلية تحتاج ملكية أسرار وتخزين، وليست APIs عامة. لا تعتمد على `source` لملف .env غير موثوق؛ dotenv وsystemd لهما صيغ متقاربة لكن ليست shell عامًا. لا توجد كلمة مرور مدير منشورة أو ترقية من صفحة العميل.

## 4. التشغيل والوكيل

القوالب في `deploy/systemd/`:

- `shamaa.service`: Uvicorn، worker واحد وحد 100 طلب متزامن، دون access log، الثقة بـforwarded headers من 127.0.0.1 فقط.
- `shamaa-mail.service`: عامل إرسال/إعادة محاولة مستقل كل 15 ثانية.
- `shamaa-backup.service` و`.timer`: أداة تدوير مشفرة يوميًا قرابة 02:00 UTC، بمهلة عشوائية حتى 10 دقائق واحتفاظ 14 يومًا كمثال.

راجع المسارات والمستخدم والصلاحيات وأنشئ المجلدات أولًا، ثم ينسخ المشغّل القوالب إلى systemd ويشغّل `daemon-reload` ثم يفعّل الخدمات التي اختبرها. **لم تُنسخ/تُفعّل هذه الوحدات هنا**. مثال بعد الإعداد الفعلي:

```bash
sudo systemctl enable --now shamaa.service shamaa-mail.service
# شغّل مهمة النسخ يدويًا أولًا وافحص الاستعادة والنسخة الخارجية
sudo systemctl start shamaa-backup.service
sudo systemctl enable --now shamaa-backup.timer
sudo systemctl list-timers shamaa-backup.timer
```

القالب يقيد الكتابة إلى مجلد البيانات/النسخ ويستخدم UMask 0077. هذه hardening بداية وليست عزلًا كاملًا أو secret manager؛ مهمة النسخ تعمل بمستخدم الخدمة نفسه، فلا تفترض عزل مفتاحها عن عملية خبيثة تملك ذلك المستخدم. ارفع مستوى فصل حساب النسخ/الخزنة بحسب نموذج التهديد.

مثال وكيل Nginx موجود في `deploy/nginx.conf.example` ويحتاج نطاقًا وشهادة حقيقيين. لا تعرض `.env` أو جذر المشروع أو data كـroot ويب، ولا تفعّل cache عامًا لمسارات API الخاصة. إن كان الوكيل على مضيف آخر، غيّر نطاق الثقة إلى عناوينه الدقيقة واختبر IP وOrigin؛ لا `--forwarded-allow-ips='*'` على منفذ عام.

في Nginx/المضيف/CDN: لا تسجل query/body أو Cookies/Authorization أو روابط تأكيد/استعادة، وحدد حجم/مهلة الطلب والحدود العامة. ضبط الوكيل لا يتم آليًا من إعداد Python.

## 5. الصحة والمراقبة والبريد

`GET /healthz` يتحقق من الوصول إلى مخطط/إعداد قاعدة v1، وليس مجرد أن ملفًا فارغًا يمكن فتحه. في الإنتاج قد تحتاج اسم Host الصحيح عند فحص الاتصال الداخلي:

```bash
curl --fail -H 'Host: YOUR_REAL_DOMAIN' http://127.0.0.1:8000/healthz
```

راقب: فشل/زمن الطلب، busy/5xx، مساحة القرص والوسائط/النسخ، عمر آخر نسخة خارجية قابلة للاستعادة، انتهاء الشهادة، queue البريد/الفشل ومحاولاته. هذه المراقبة والتنبيهات **غير موصولة بخدمة خارجية حاليًا**. لا يصح الاستنتاج من health وحده أن البريد/النسخ أو شريك الشحن يعمل.

```bash
.venv/bin/python -m server.cli mail-status
.venv/bin/python -m server.cli mail-worker --once
```

حالة `file` تعني كتابة محلية لا إرسال. `sent` تعني قبول SMTP من النقل، لا ضمان Inbox. بعد 5 محاولات يتوقف الإرسال التلقائي لذلك السجل؛ يلزم فحص السبب وإجراء تشغيل موثق، أو طلب رابط جديد من المستخدم عند انتهاء السابق. لا تعِد إرسال طابور قديم مستعاد بلا مراجعة. تنبيهات فشل العامل لا تُعد مفعّلة لمجرد وجود summary في الإدارة.

## 6. النسخ المشفر

بمفتاح نسخة مستقل داخل بيئة مهمة النسخ أو إدخاله في prompt مخفي:

```bash
.venv/bin/python -m server.cli backup --output /PRIVATE_BACKUP_DIR/manual-snapshot.shama
.venv/bin/python -m server.cli backup-rotate --directory /PRIVATE_BACKUP_DIR/rotated --keep-days 14
```

استبدل المسارات بمجلد خاص تملكه الخدمة، لا بجذر الملفات/المشروع أو مجلد البيانات الحي. لا تضع المفتاح في argv أو اسم ملف أو log. النسخة المحلية لا تكفي وحدها.

الأرشيف يحتوي:

- لقطة متسقة باستخدام SQLite backup API؛ لا `cp` لقاعدة WAL حية مع إهمال WAL.
- سجل تعريف النسخة ووسائط media المشار إليها في اللقطة، بأسمائها الثابتة.
- مفتاح التطوير داخل التشفير في التطوير فقط؛ **مفتاح تشفير الإنتاج/ملف البيئة غير مضمن**.
- لا كود التطبيق أو إعدادات DNS أو كلمات مرور مزودين أو بريد .eml خارجي؛ احتفظ بالكود وإعدادات الاستعادة الخاصة بصورة مستقلة وآمنة.

AES-GCM بتوثيق المحتوى، nonce عشوائي، مفتاح 32 بايت بترميز URL-safe base64، وملف لا يستبدل أرشيفًا موجودًا. التدوير لا يحذف إلا أسماء أرشيفات الأداة المطابقة بالضبط، بعد نجاح إنشاء نسخة جديدة، ولا يحذف symlinks/ملفات أخرى. راقب فشل/توقف النسخة ومساحة scratch؛ لا تنقل ملفًا وهو قيد الإنشاء. اجعل النقل الخارجي **بعد نجاح أمر النسخ**، مع تحقق سلامته.

### النسخة الخارجية

اختر وجهة خاصة خارج الجهاز/الحساب الرئيسي إن أمكن، مع تشفير ونقل موثوق وحساب أقل صلاحية وسياسة احتفاظ، واختبر تنزيلًا فعليًا. لا مفاتيح وصول للوجهة مضمنة أو نسخ خارجي منفذ هنا. وفّر قناة تنبيه لفشل النقل، ولا تحذف المحلي قبل تأكيد وجود نسخة خارجية صالحة. لا تعتمد على مزامنة حذف فورية بلا إصدارات/حماية من برمجيات الفدية.

## 7. تمرين استعادة آمن

استعمل بيئة معزولة وقرصًا كافيًا، ومفتاح النسخ الصحيح، ومفتاح التطبيق/الإصدار الموافقين:

```bash
.venv/bin/python -m server.cli restore --input /PRIVATE_BACKUP_DIR/manual-snapshot.shama --to /PRIVATE_RESTORE_DIR/new-restored
```

- الوجهة **يجب ألا تكون موجودة**. لا تستهدف قاعدة حية أو مجلد المشروع؛ الأداة لا تستبدلهما.
- يتم توثيق وفك التشفير قبل استخراج الأرشيف، ومنع symlink/المسارات غير المسموحة والتكرار، وحد استخراج 10GiB، وفحص integrity/foreign keys/schema والوسائط المرجعية.
- تُبطل كل الجلسات ورموز التحقق/إعادة التعيين غير المستخدمة، ويُحجر طابور الإرسال المعلق حتى مراجعة المشغّل. لن تعود روابط التطوير القديمة فعالة.
- لا تفك/تستخرج الأرشيف يدويًا في static. النسخة المستعادة بيانات حساسة، وليست ملف اختبار عام.
- الإنتاج يحتاج مفتاح تشفير التطبيق الأصلي لفك MFA. **تغيير المفتاح بلا ترحيل إعادة تشفير ليس تدويرًا صالحًا.**

بعد الاستعادة: عيّن `SHAMAA_DB` و`SHAMAA_DATA_DIR` في بيئة معزولة إلى **المجلد المستعاد كله بما فيه media**، وليس القاعدة وحدها. اضبط ملكية/صلاحيات الملفات، وبريد الاختبار وعدم الفهرسة، وجرّب الدخول بـMFA وطلبًا/مخزونًا/صورة وسجل تاريخ، ثم وثق مدة الاستعادة والفقد الممكن. بيانات العملاء لا ترسل إلى staging عام.

حدّد هدف RPO/RTO بعد قياس فعلي. يومية النسخ مثال إعداد، **ليست ضمان عدم فقد آخر 24 ساعة** إذا فشلت المهمة/النقل. يجب إجراء تمرين تشغيلي دوري مثل شهريًا وفق سياسة المالك؛ اختبارات الوحدة لا تغني عن تمرين المضيف/الوجهة الخارجية.

## 8. التحديث والتراجع

1. احفظ معرف الإصدار/commit والاعتماديات وملفات البيئة الخاصة بأمان، وخذ نسخة جديدة وتحقق من تنزيلها.
2. اختبر الإصدار والمخطط والترقية في staging. لا تغير schema.sql مباشرة على إنتاج وتفترض أنه ترحيل.
3. نافذة صيانة قصيرة: أوقف الكتابات/الخدمات عند الحاجة، بدّل رابط `current` إلى إصدار اختُبر، ثم ابدأ وراقب الصحة وطلبًا محدودًا.
4. إن كان المخطط متوافقًا، أعد الإصدار السابق واختبر. إن كان المخطط أحدث من التطبيق القديم، **لا تشغّل القديم على القاعدة الجديدة**؛ نفّذ خطة ترحيل عكسي مختبرة أو استعد لقطة إلى مجلد جديد بعد إيقاف الكتابات.
5. الاستعادة قد تفقد طلبات أحدث من اللقطة. راجع الأثر مع البائعين/المشترين والمحاسبة، ولا تعِد إنشاء طلبات/صرف مكرر عميانيًا. احتفظ بالقاعدة المتوقفة للتحليل الآمن.
6. على كل تحديث static غيّر إصدار cache في `static/sw.js` ومرجع اختباره، واختبر online/offline والصفحات الخاصة. النسخة الحالية `shamaa-public-v1.0.3`.

لا يوجد ترحيل/rollback إنتاج منفذ في هذه الجلسة. قوالب systemd وNginx ليست نظام نشر تلقائيًا ولا بديلًا عن مشغّل مؤهل.
