# المراحل ومعايير القبول

## قاعدة التنفيذ

يُنجز كل نطاق ويُختبر قبل إضافة خدمات مالية أو ميزات أوسع. كلمة «مُنفّذ» تعني وجود مسارات وبيانات وصلاحيات وتدفق يعمل محليًا؛ **لا تعني نشر إنتاج أو اعتماد قانوني/أمني**. دليل الاختبارات الفعلي في [VERIFICATION.md](VERIFICATION.md).

## المرحلة 2 — اكتمال السوق والخدمة

تنفذ في دفعات صغيرة، لا تضاف كلها كتبديل إعداد واحد:

### التقدم — دفعة 1: حالة المنتج المستعمل

- تصنيف المنتج المادي إلى جديد أو مستعمل في إدخال البائع والكتالوج العام.
- وصف حالة المستعمل إلزامي (10 أحرف على الأقل)، ويظهر للمشتري قبل الإضافة للسلة.
- تُحفظ الحالة والوصف كلقطة ثابتة في سطر الطلب، فلا يغيّر تعديل الإعلان لاحقًا وصف ما اشتراه المشتري.
- ترحيل SQLite من `user_version=1` إلى `2` يحافظ على البيانات القديمة ويعامل السلع القائمة كجديدة افتراضيًا؛ ترحيل PostgreSQL المقابل لا يفتح RLS ولا يغيّر الصلاحيات.
- المنتجات الرقمية ما تزال غير مدعومة؛ لا تُفعّل قبل تخزين خاص وروابط تنزيل مؤقتة واختبارات ملكية الطلب وحدود التنزيل.
- القبول: اختبار حقول الخادم، بيانات الإعلان العامة، لقطة الطلب، ترقية قاعدة قديمة، ومخطط PostgreSQL 17.


1. **المستعمل والرقمي:** condition واضح ومراجعة، ملفات خاصة ومفاتيح/صلاحيات تنزيل من الطلب، فحص ملفات وحدود تنزيل وروابط موقعة وانتهاء، وسياسة استرداد واقعية. لا تعرض «منتج رقمي» قبل تأمين الوصول. القبول: شخص آخر/رابط منتهي/طلب غير مؤهل لا ينزل الملف؛ لا تسريب تخزين عام.
2. **كتالوج ومخزون أوسع:** متغيرات وSKU فرعي، صور متعددة، مواقع/حجوزات/حد تنبيه واستيراد CSV بمرحلة معاينة. القبول: طلب متغير واحد لا يخصم متغيرًا آخر، والاستيراد قابل للتحقق والتراجع.
3. **تفاعل وخدمة:** رسائل محفوظة ذات صلاحيات، تقييم بعد شراء مؤكد دون تقييمات مولدة، إبلاغ/نزاع/مرتجعات وتتبع أدلة ومهل، قناة دعم حقيقية. القبول: لا يرى شخص محادثة/عنوانًا لا يخصه، والتقييم له طلب مؤهل.
4. **عروض وتشغيل:** كوبونات وحدود تكديس واستخدام ذرية، ولاء وانتهاء، فواتير/إيصالات تشغيلية وتسوية يدوية وتقارير وصادرات. لا وصف الفواتير بأنها رسمية قبل اعتماد متخصص. القبول: تطبيق الاستهلاك والخصم من الخادم مرة واحدة.
5. **نمو وربح:** مواضع إعلانية موسومة، اشتراكات اختيارية، تسويق بالعمولة بروابط وإسناد حقيقي ومكافحة إساءة؛ لا بيع الثقة أو أرقام انتشار مختلقة. القبول: القياس من أحداث حقيقية وموافقة الخصوصية، لا زيادات أرقام شكلية.
6. **حقوق الحساب:** تصدير ذاتي بعد إعادة التحقق وحذف/إخفاء منضبط مع استثناءات حفظ السجلات القانونية ومواعيد إتلاف النسخ؛ مراجعة قانونية وتدقيق صلاحيات التصدير.

## المرحلة 3 — التكاملات الحقيقية

- **الدفع بالأردن:** مقارنة مزودين ودعم JOD والتجار الأردنيين والتسوية والاسترداد والرسوم والتصاريح أولًا. sandbox ثم توقيع webhooks ومنع تكرارها ومصالحة ودفعات فاشلة/معلقة، ثم إنتاج محدود. لا تخزين بطاقات، ولا اعتبار redirect نجاحًا نهائيًا.
- **الشحن:** عقود وأسعار فعلية وتغطية وجغرافيا وwebhooks، فشل/تكرار/إلغاء الملصق وتحديث الحالة؛ لا «ناقل متصل» قبل اختبار طرفه.
- **الصرف والمحاسبة:** أموال محصلة ومطابقة، فترات نزاع/حجز، منع صرف مزدوج، فصل المنشئ والمعتمد، إعادة مصادقة وسجل غير قابل للتلاعب، مراجعة محاسب ومزود مرخص حسب الحالة. لا تحويل بناء على تغيير status وحده.
- **AI اختياري:** adapter مستقل ومعطل افتراضيًا، مفاتيح خلفية، سقف تكلفة وبيانات مصرح بها وموافقات، قابل للاستبدال. مواصفات المنتج من البائع لا من اختلاق AI، ولا حكم احتيال/مال نهائي آلي.
- **SEO/قياس/مخاطر:** تصيير محسن ومراجعة structured data على حقائق فقط، قياس بإذن وحفظ محدود، إشارات اشتباه مع مراجعة بشرية وقابلية اعتراض، لا وعود ترتيب/ربح.

لكل مزود: تحقق مؤرخ من حدود المجاني والشروط التجارية ومعالجة البيانات والتصدير/النسخ، وقائمة تكاليف وموافقة المالك قبل إضافة المفاتيح.

## المرحلة 4 — المؤسسات والتوسع

- PostgreSQL وترحيلات موثقة وقفل معاملات وخطة استعادة، وتخزين كائنات خاص ونسخ متعددة المواقع؛ لا قرص SQLite مؤقت على عدة instances.
- مؤسسات وموظفون بصلاحيات دقيقة ودعوات وإلغاء وصول وفصل مؤسسات ومنح أقل صلاحية؛ اختبارات عزل بين المستأجرين.
- دول وعناوين وتغطية وضرائب/تقريب وعملات متعددة بقيود مالية واختبارات، دون كسر JOD والفلس.
- مهام وطوابير ومراقبة/تنبيهات واختبارات حمل فعلية وموازن بعد إثبات الحاجة؛ خطة كلفة/توقف/تراجع.
- API بإصدار وتوثيق ومصادقة مناسبة لتطبيق Android، ثم تطوير/اختبار وإطلاق متجر تطبيقات مستقل. PWA الحالي لا يعني أن Android الأصلي مكتمل.

## تعريف «انتهت المرحلة»

تغييرات بيانات مرقّمة + صلاحيات خادم + اختبارات قبول/فشل/تزامن مناسبة + مستند تشغيل/استعادة وتكلفة + تجربة RTL/LTR وإتاحة + موافقات خارجية لازمة. الميزات المعطلة/المؤجلة لا تظهر كأزرار دفع أو توثيق أو خدمة وهمية. لا تُعلَن المرحلة التالية مكتملة بمجرد تصميم صفحاتها.

### التقدم — دفعة 2: معرض صور المنتج

- جدول `product_images` منفصل مع ترتيب الصور، وترحيل الصورة الأساسية الحالية إلى الموضع الأول.
- الصور الإضافية مملوكة للبائع، وبحد أقصى 8 صور للمنتج، مع منع تكرار الصورة.
- تحديث المعرض يتطلب نسخة المنتج الحالية؛ تحديث معرض منتج منشور يعيده للمراجعة قبل إعادة النشر.
- الصور لا تصبح عامة بمجرد الرفع؛ مسار الصور العامة لا يقبل إلا وسائط مرتبطة بمنتج منشور ومتجر نشط وحساب بائع نشط.
- PostgreSQL يفعّل ويفرض RLS على الجدول الجديد ويبقيه دون سياسات ودون منح PUBLIC؛ لم يتغير نطاق Data API.
- القبول: ملكية الوسائط، الترتيب، التزامن، منع الوصول العام للصور غير المنشورة، ترقية SQLite ومخطط PostgreSQL 17.

### التقدم — دفعة 3: بنية متغيرات المنتج

- ترحيل v4 يضيف جدول المتغيرات، ويجعل مفتاح السلة وسطر الطلب مميزًا بالمتغير، مع حفظ SKU والخصائص لقطةً وقت الشراء.
- مخطط SQLite وPostgreSQL يجهّز مخزونًا وسعرًا مستقلين لكل تركيبة، ويبقي المتغيرات في PostgreSQL تحت FORCE RLS ومن دون سياسات عامة.
- اكتمل مسار البائع لإدارة المتغيرات ذات SKU وخصائص وسعر ومخزون مستقل، مع نسخة متفائلة تمنع حفظ نموذج قديم.
- اختيار المتغير مطلوب للمنتج الذي يملك متغيرات؛ السلة تفصل كل تركيبة، وعرض السعر والمخزون مأخوذ من الخادم، لا من قيمة يرسلها المتصفح.
- تحفظ سطور الطلب SKU والخصائص والسعر كلقطة شراء؛ الخصم ذري لكل متغير، والإلغاء يعيد مخزون كل خيار مرة واحدة.
- تعديل متغيرات منتج منشور يعيده للمراجعة، ولا يعود عامًا إلا بعد اعتماد الإدارة.
- قبول الخادم: اختبار المتغيرات يغطي اختلاف SKU والسعر والمخزون، رفض تجاوز الكمية وغياب الاختيار، لقطة الطلب، الخصم والاستعادة. قبول المتصفح: إنشاء/تعديل المتغيرات ومراجعتها واختيارها وإضافتها منفصلة للسلة.
- CI المؤكد: التشغيل [42907624194](https://github.com/mohammadalshlool425-lab/shamaa-store/actions/runs/42907624194) نجح على commit `902cea9316dcfeb8e762e596fa932d3fc85f7abd`، مع 6/6 سيناريوهات متصفح.
- PostgreSQL يبقى fail-closed: الجداول تحت FORCE RLS بلا سياسات وصول عامة ولا منح تشغيل للمتصفح؛ نجاح مخطط PostgreSQL واختباراته لا يشغّل قاعدة الإنتاج ولا يفتح Data API.

### التقدم — دفعة 4: المراسلات الخاصة بين المشتري والبائع (مكتمل)

- لكل شحنة بائع محادثة واحدة مرتبطة بـ `seller_order_id`؛ لا يختار العميل هوية المشتري أو البائع، بل تُشتق من الطلب والمتجر في قاعدة البيانات.
- يقتصر إنشاء المحادثة والإرسال على حساب موثّق البريد، ويُسمح بالقراءة للمشاركين فقط؛ يحصل غير المشارك على 404 لمنع كشف وجود المحادثة.
- الرسائل نصية فقط، مع تطبيع Unicode/أسطر الكتابة، وحد 4000 حرف، ومحدد سرعة، ومفتاح idempotency يمنع التكرار حتى عند تزامن الطلبات.
- تنبيهات الطرف الآخر عامة ولا تتضمن نص الرسالة؛ سجل التدقيق يحفظ معرفات وأحداثًا لا محتوى المستخدم.
- الرسائل append-only؛ تمنع قيود/مشغلات قاعدة البيانات تعديل الرسالة أو حذفها وتتحقق أن المرسل هو مشتري الطلب أو مالك متجر الشحنة.
- واجهة عربية/إنجليزية متجاوبة: زر مراسلة من الشحنة، قائمة محادثات، عرض آخر 100 رسالة وإرسال الرد. لا توجد مرفقات ولا مشاركة عنوان أو هاتف في المحادثة.
- تم اختبار نص يحتوي وسم HTML؛ يظهر كنص ولا ينشئ عنصر script. واجتاز فحص axe بعد رفع التباين إلى 5.77:1.
- SQLite وPostgreSQL migration `0005` يضيفان جدولي `conversations` و`messages`. PostgreSQL يحافظ على ENABLE+FORCE RLS دون سياسات وصول أو منح PUBLIC، ولم يُفعّل runtime اتصال الإنتاج.

### التقدم — دفعة 5: تقييمات المشتريات المؤكدة (مكتملة خادميًا)

- لا يمكن إنشاء تقييم إلا من بند طلب يخص الحساب نفسه وشحنته في حالة delivered؛ لا يعتمد الخادم على product_id أو buyer_id يرسلهما العميل.
- تقييم واحد لكل بند طلب، نجوم 1–5 ونص محدود، بحالة pending افتراضيًا؛ لا يظهر في متوسط المنتج أو الصفحة العامة قبل اعتماد المشرف.
- لا يمكن تقييم منتج لم يُشترَ أو شحنة ملغاة/غير مكتملة، ولا تكرار تقييم البند نفسه؛ شراء جديد مؤهل قد يمنح أهلية مستقلة.
- إبلاغ التقييم لا يخفيه آليًا ولا يغير متوسطه؛ يفتح بلاغًا للمراجعة مع منع بلاغات الحساب المكررة، وسجل إجراءات الإدارة.
- لا تُنشر أسماء كاملة أو هواتف المشترين؛ واجهة التقييم تعرض شارة شراء موثّق من دون كشف معلومات الطلب.
- SQLite وPostgreSQL migration 0006، مسارات المشتري والإدارة، واختبارات الملكية والمراجعة والبلاغات موجودة. أحدث CI قبل دفعة الشكاوى مرّ على الوظائف الثلاث.

### التقدم — دفعة 6: شكاوى الشحنات (طبقة البيانات والواجهة الأساسية)

- سجل شكوى واحد لكل شحنة، ويُفتح من مشتري الطلب نفسه بعد انتقال الشحنة إلى shipped أو delivered؛ تُشتق هوية المشتري والبائع من الطلب والمتجر في قاعدة البيانات.
- في حالة shipped يقتصر السبب على عدم الاستلام؛ وبعد delivered تُقبل أسباب التلف أو الخطأ أو النقص أو مخالفة الوصف أو سبب آخر.
- نافذة فتح أولية قدرها 14 يومًا من حدث الشحن/التسليم المسجل، ومهلة رد تشغيلية أولية 48 ساعة للبائع. هذه قيم تشغيلية قابلة للمراجعة وليست وعدًا قانونيًا أو مدة ضمان/إرجاع مقررة.
- مراسلات الشكوى نصية وخاصة بالمشتري والبائع؛ سجل الأحداث append-only، وتغيير الحالة لا يتم إلا عبر رد الطرف المناسب أو قرار مشرف موثّق مع MFA حديث.
- أضيفت واجهة عربية/إنجليزية لفتح الشكوى من صفحة الطلبات، ومتابعة سجلها والردود في /cases، وروابط من مساحة البائع ولوحة الإدارة، مع قرار إداري بعد إعادة تحقق أمني حديث.
- SQLite migration 0007 وSupabase PostgreSQL migration 0007، وحراس قاعدة البيانات، وفحوص RLS وواجهات API واختبارات الأمن أُضيفت إلى الفرع.
- المرفقات ما زالت غير مفعّلة؛ لا تُعرض سياسات RLS أو صلاحيات Data API عامة، ولم تُربط بيئة التشغيل بقاعدة Supabase الحية. لا يُنشأ رد مالي أو حركة ledger أو صرف تلقائي عند فتح الشكوى أو إغلاقها.
- القبول المتبقي لإكمال دفعة 6: اختبارات متصفح مخصصة لتدفق الشكوى ورد المشتري والبائع وقرار الإدارة، ثم تصميم مرفقات خاصة مع فحص النوع والحجم والوصول واختبارات إتاحتها. لا تُعتبر الدفعة مكتملة قبل ذلك.
