# خطة ربط شمعة بـ Supabase دون كسر التطبيق

> سجل قرار هندسي — 9 نوفمبر 2026. هذه الوثيقة تصف حالة المستودع ومشروع Supabase والخطوة الآمنة التالية. لا تعني أن التطبيق أصبح متصلًا بـ Supabase.

## 1. الحالة التي تم التحقق منها

- المستودع الحالي: `mohammadalshlool425-lab/shamaa-store`، الفرع الأساسي `main`.
- فرع العمل: `agent/supabase-integration`، أُنشئ من `main` ولم تُعدّل ملفات `main`.
- التطبيق الحالي يعمل بـ FastAPI وSQLite، ومخططه الفعلي في `server/schema.sql`. طبقة الاتصال في `server/database.py` وتستعمل `sqlite3` وواجهات SQLite.
- الهوية الحالية مخصصة للتطبيق: جدول `users` بمعرّف INTEGER، كلمات مرور scrypt، جلسات Cookies، رموز تأكيد البريد/استعادة كلمة المرور، وMFA للمشرف. الصلاحيات تطبقها تبعيات FastAPI واستعلامات الخادم.
- المستودع لا يحتوي إعدادًا فعليًا لـ Supabase؛ ملف `.env.example` لا يتضمن عنوان مشروع Supabase أو مفتاحه أو اتصال PostgreSQL.
- مشروع Supabase المتاح هو `wksndkftoqjeibmxexad`. أُنشئت فيه جداول أولية في مخطط `public` تستخدم `auth.users` ومعرّفات UUID ونموذج بيانات مختلفًا.

## 2. لماذا لا يجوز توصيل التطبيق بالجداول الحالية مباشرة؟

المخططان ليسا متوافقين بمجرد تغيير عنوان قاعدة البيانات:

| التطبيق الحالي | مخطط Supabase الأولي |
|---|---|
| `users.id` عدد صحيح وهوية مخصصة | `auth.users.id` UUID |
| كلمات المرور والجلسات في التطبيق | مصادقة Supabase غير موصولة بالتطبيق |
| المال محفوظ كأعداد صحيحة بالفلس (1 JOD = 1000 fils) | حقول مالية NUMERIC بالدينار |
| `stores.status`, `products.status` وحالات مراجعة محددة | أعمدة وحالات مختلفة |
| `orders` + `seller_orders` + `order_items` + `order_events` + `inventory_movements` | جداول أولية لا تطابق جميع حقول وتدفقات التطبيق |
| `ledger` يسجل استحقاق عمولة COD عند التسليم | `commission_ledger` بنموذج مختلف |

إعادة توجيه `sqlite3` إلى Postgres أو استخدام مفتاح إداري داخل المتصفح سيؤدي إلى فشل التطبيق أو تجاوز حدود الصلاحيات. لذلك لم تتم إضافة مفاتيح أو تغيير كود التشغيل لهذا الغرض.

## 3. المسار الموصى به

الهدف هو جعل Supabase PostgreSQL قاعدة البيانات الأساسية، مع الحفاظ على تدفقات التطبيق الحالية واختباراتها، دون إجبار المشروع على تغيير الهوية دفعة واحدة.

**قرار التنفيذ المقترح:**
1. الاحتفاظ بنظام الهوية الحالي مؤقتًا في مرحلة النقل، وعدم إنشاء حسابات مكررة أو فقد الجلسات/كلمات المرور.
2. إنشاء مخطط خاص غير مكشوف عبر Data API مثل `shamaa_app` يطابق نموذج التطبيق الفعلي، بدل إعادة استعمال أسماء الجداول المتضاربة في `public`.
3. تحويل مخطط SQLite إلى PostgreSQL مع الحفاظ على معرّفات التطبيق والأموال بالفلس، وقيود الطلبات والعمولات وسجلات الأحداث.
4. تفعيل RLS على كل جدول حساس في المخطط الخاص. يمرّر الخادم هوية المستخدم بعد التحقق من جلسة التطبيق في متغير PostgreSQL محلي للمعاملة، مثل `app.current_user_id`; وتستخدم السياسات `current_setting(..., true)` مع رفض الوصول عند غياب الهوية.
5. استخدام حساب قاعدة بيانات مخصص للتطبيق بصلاحيات أقل، لا يكون مالك الجداول ولا superuser ولا يملك `BYPASSRLS`. تُستخدم معاملات قصيرة و`SET LOCAL`/إعدادات transaction-local حتى لا تنتقل هوية طلب إلى اتصال آخر في pool.
6. إبقاء كلمات المرور واتصالات قاعدة البيانات ومفاتيح التشفير في أسرار بيئة الخادم فقط؛ لا يوضع أي سر إداري في JavaScript أو ملفات Git.
7. بناء محول PostgreSQL واختبارات مطابقة لعقد `Database` الحالي، ثم تشغيل اختبارات الحسابات والملكية والطلبات المتزامنة والعمولات والنسخ/الاستعادة على قاعدة اختبار منفصلة.
8. بعد اجتياز الاختبارات، تنفيذ ترحيل بيانات موثق من SQLite مع مقارنة أعداد الصفوف والمجاميع المالية وسجلات المخزون، ثم تحويل التشغيل إلى Postgres. لا تُحذف قاعدة SQLite الأصلية حتى نجاح التحقق والاستعادة.

هذا المسار يسمح بالإبقاء على نظام الهوية الحالي أثناء الانتقال، ثم يمكن تقييم نقل الحسابات إلى Supabase Auth لاحقًا كعملية مستقلة ومخططة.

## 4. شروط أمان لا تقبل الاختصار

- لا تستخدم `service_role` أو secret key في المتصفح أو PWA أو أي ملف يبدأ بـ `NEXT_PUBLIC_`.
- لا تجعل حساب التطبيق مالكًا للجداول أو دورًا يتجاوز RLS. يجب أن تفشل السياسات مغلقة عند غياب `app.current_user_id`.
- لا تعتمد على `user_metadata` أو بيانات يرسلها المتصفح لتحديد دور admin/staff.
- لا تسمح للعميل بكتابة سعر الطلب أو العمولة أو صافي البائع أو حالة الدفع؛ يحسبها الخادم داخل معاملة ذرية.
- لا يعتبر تحويل COD إلى `delivered` إثباتًا بأن المنصة قبضت العمولة نقدًا.
- لا تختبر الترحيل على بيانات إنتاج؛ استخدم نسخة اختبار غير حساسة أولًا.
- لا تُحذف أو تُعاد تسمية الجداول الـ27 التي أُنشئت في `public` في هذا المشروع ضمن هذه الخطوة. أي تنظيف أو توحيد لاحق يحتاج مراجعة مستقلة وخطة تراجع.

## 5. ما الذي لم يحدث بعد؟

- التطبيق لا يتصل بعد بمشروع Supabase.
- لم يتم ترحيل بيانات SQLite إلى PostgreSQL.
- لم يتم تحويل تسجيل الدخول إلى Supabase Auth.
- لم يتم إنشاء محول PostgreSQL للتطبيق.
- لم يتم إعداد أو تخزين كلمة مرور اتصال قاعدة البيانات في أي مستودع.
- وجود مخطط أولي وفحص RLS لا يعني أن التطبيق نفسه أصبح آمنًا أو متصلًا به.

## مراجع Supabase

- [Supabase Auth](https://supabase.com/docs/guides/auth): ربط مصادقة المستخدمين مع JWT وRLS.
- [RAG with Permissions — direct Postgres connection and custom session variable](https://supabase.com/docs/guides/ai/rag-with-permissions): مثال رسمي على استخدام متغير جلسة مخصص لتطبيق سياسات RLS عندما تكون هوية المستخدم موجودة خارج Supabase Auth.
- [Securing your data](https://supabase.com/docs/guides/database/secure-data): مبادئ الصلاحيات وسياسات RLS.



## 6. التنفيذ الفعلي — تأسيس مخطط PostgreSQL

بتاريخ 9 نوفمبر 2026 أُضيف الملف `supabase/migrations/0001_shamaa_app_foundation.sql` إلى فرع العمل، وطُبّق تعريفه على مشروع Supabase `wksndkftoqjeibmxexad` بعد مراجعة عدم المساس بمخطط `public`.

- أُنشئ مخطط خاص باسم `shamaa_app` يحوي 19 جدولًا تطابق نموذج SQLite الحالي الأساسي، مع مفاتيح خارجية وقيود وفهارس أولية.
- بقيت القيم المالية أعدادًا صحيحة بالفلس، ومعرّفات السجلات BIGINT، والطوابع الزمنية بصيغة Unix seconds لتسهيل توافق التطبيق.
- فُعّل RLS وFORCE ROW LEVEL SECURITY على الجداول الـ19. لم تُنشأ سياسات أو صلاحيات وصول للتطبيق بعد؛ لذلك الوصول مغلق افتراضيًا. ظهور تنبيه advisor عن غياب السياسات متوقع في هذه المرحلة، وليس تصريحًا بأن سياسة الوصول اكتملت.
- تحقق الاستعلام من وجود 19 جدولًا مع RLS مفعّل على 19/19، ولم توجد بيانات في جداول المستخدمين والمنتجات والطلبات وقت التحقق.
- لم تُنقل بيانات SQLite، ولم يُربط FastAPI بالمخطط الجديد، ولم تُنشأ كلمة مرور اتصال أو صلاحيات تشغيل. مخطط `public` السابق لم يُحذف أو يُعدّل في هذه الخطوة.

**الخطوة التالية:** تنفيذ محول PostgreSQL متوافق مع واجهة `Database`، وإضافة اختبارات تكامل ضد PostgreSQL، ثم تصميم سياسات RLS ومتغير هوية transaction-local ودور تشغيل محدود الصلاحيات قبل منح التطبيق أي وصول.

## 7. عقد PostgreSQL واختبار مسارات الرفض — 9 نوفمبر 2026

أضيفت وظيفة postgres-schema إلى سير عمل GitHub Actions وتستخدم PostgreSQL 17 نظيفًا في كل تشغيل، دون الاعتماد على قاعدة البيانات الحية أو بياناتها.

تشمل اختبارات العقد الآن:
- التحقق من وجود الجداول الـ19 وتفعيل ENABLE ROW LEVEL SECURITY وFORCE ROW LEVEL SECURITY عليها جميعًا.
- التأكد من عدم وجود سياسات وصول مبكرة، ومن وجود حراس السجلات الأربعة غير القابلة للتعديل.
- التحقق من أعمدة نموذج التطبيق الأساسية في جميع الجداول الـ19.
- تجربة إدخال علاقات صحيحة داخل معاملة يتم التراجع عنها.
- تجربة مسارات يجب أن تفشل: البريد المكرر مع اختلاف حالة الأحرف، المخزون السالب، كمية السلة غير الصحيحة، وإجمالي الطلب غير المتسق.
- التحقق عمليًا من رفض تحديث سجل التدقيق أو حذفه.

أُنجز التشغيل السابق 42696029783 بنجاح على وظائف الخادم وPostgreSQL والمتصفح. التشغيل الحالي 42697024534 على commit f0b48bba5bae943a4770c2935be2fd46bff0e644: وظيفة PostgreSQL نجحت، بينما اختبارات الخادم لا تزال قيد التنفيذ وقت تحديث هذه الوثيقة.

**ما لا يثبته هذا العقد:** لا يشغّل FastAPI على PostgreSQL بعد، ولا يثبت سياسات عزل مستخدمين فعلية؛ فالمخطط مغلق بلا سياسات، ولا توجد بيانات تطبيق منقولة.

## 9. ترحيل 0008 — metadata لأدلة الشكاوى الخاصة

أضيف `supabase/migrations/0008_case_attachments.sql` إلى فرع العمل، مع نظيره SQLite `server/migrations/0008_case_attachments.sql`. يضيف الجدول `shamaa_app.order_case_attachments` روابط الشكوى والرافع والدور ومفتاح التخزين ونوع المحتوى والحجم وSHA-256 ووقت الإضافة.

- يقتصر نوع المحتوى المسجل على `image/webp` بعد أن يفك الخادم الصورة ويتحقق من تنسيق JPEG/PNG/WebP ثم يعيد ترميزها ويزيل بيانات EXIF.
- يشترط trigger أن الرافع مشارك نشط وموثّق البريد، وأن تكون الشكوى غير مغلقة؛ metadata لا تقبل UPDATE أو DELETE. حد التطبيق خمس صور و25MiB لكل شكوى، وخمسة ميغابايت لكل صورة.
- يفعّل الترحيل ENABLE + FORCE RLS ويمنع سياسات أو منح PUBLIC. هذا تصميم مغلق للمخطط وليس تصريحًا بفتح Data API أو تشغيل FastAPI على Supabase.
- ملفات الصور في التنفيذ الحالي محفوظة على مضيف التطبيق داخل مجلد بيانات خاص `case-attachments/`، لا في Supabase Storage. روابط التنزيل تمر عبر FastAPI مع تحقق العضوية في كل طلب و`Cache-Control: no-store`. يجب اختبار صلاحيات الوصول مجددًا قبل أي نقل إلى private bucket أو object storage.
- أُضيفت الملفات إلى النسخ المشفر والاستعادة مع التحقق من الحجم وSHA-256. لا يكفي نسخ قاعدة PostgreSQL وحدها عند تشغيل هذا التخزين المحلي؛ يلزم نسخ مجلد الأدلة الخاص بالتطبيق بصورة متسقة.
- يرفع CI ترحيل 0008 إلى PostgreSQL 17 مؤقتًا ويتحقق من 28 جدولًا ENABLE+FORCE RLS، ووجود metadata guards، وغياب السياسات المبكرة. لا تُطبّق 0008 على مشروع Supabase الحي قبل مراجعة خطة الصلاحيات والتخزين والتشغيل والنسخ والاستعادة.

**حالة التنفيذ:** migration 0008 موجود في فرع `agent/supabase-integration` فقط. لم يُنشأ bucket على Supabase، ولم تُرسل أو تُنقل أي ملفات أو بيانات إلى مشروع Supabase، ولم يُفعّل اتصال PostgreSQL للإنتاج.
